  Holes in the row lock, which you asked me to find

  Your mechanism is right. Four things it needs that you did not say, all now in
  D10 and the design:

  - The sequence number and the timestamp must both be drawn after the lock is
    acquired. Drawing the number first leaves the inversion exactly where it
    was, since nextval ignores transactions. Same for the timestamp: now() fixed
    at transaction start can still be earlier for the transaction that commits
    later, even with the lock in place. Reading the clock after the lock fixes
    both.
  - The lock must cover the local transaction only. Holding a record row lock
    across a Salesforce call means 200 to 500 milliseconds of network time
    inside the lock, so one record would manage two to five saves a second and
    the concurrency the drain needs collapses.
  - The inbound path has to take the same lock. Otherwise an applied webhook and
    a portal save interleave on one record, and the ordering guarantee covers
    portal saves alone.
  - A save touching several records needs a fixed lock order, by record
    identifier. A contact and its customer locked in different orders by two
    transactions deadlock.

  One thing that is fine and worth knowing: sequence numbers leave gaps when a
  transaction aborts, since sequences do not roll back. Gaps do no harm to
  ordering as long as nothing assumes the numbers are contiguous.

  One scope point: the lock orders saves to the same record. Saves to different
  records stay unordered relative to each other, which is all this design needs.

  Next question: how is a portal-created record identified before Salesforce has
  given it an ID?

  - The brief says both sides may create. The webhook sample and the portal
    sample both carry recordId with a Salesforce-shaped value like
    0031A00000Abc.
  - A record created in the portal has no such value until the create call
    returns, and that call may be queued behind a six-hour outage.
  - So for up to six hours the portal holds records that exist for finance staff
    and do not exist in Salesforce.

  Option A: our own identifier is the primary key, the Salesforce ID is a
  nullable column

  - Every record gets a portal identifier at creation, generated locally.
  - A salesforce_id column stays empty until the create call returns, then gets
    filled in.
  - Everything in our system, including history rows and the outbound queue,
    refers to the portal identifier, so nothing has to be rewritten when the
    Salesforce ID arrives.
  - The cost: every inbound webhook needs a lookup from Salesforce ID to portal
    identifier.

  Option B: the Salesforce ID is the primary key, with a placeholder until it
  arrives

  - Simpler joins while a record is synced, and it forces a rewrite of every
    reference the moment the create returns.
  - Rewriting a primary key that history rows and queue entries point at, under
    load, is the kind of thing that works until it does not.

  Option C: ask Salesforce to accept an identifier we choose

  - Salesforce has an external ID field pattern used for exactly this, where an
    upsert keyed on our own value either creates or matches. I have not verified
    how it behaves for Contact and Account in this client's org, and I would
    mark it an assumption until checked.
  - If available it removes the two-phase create entirely, since we could write
    by our own key from the first call.

  What I would pick

  - A, with C investigated as an improvement on the outbound path.
  - A portal identifier that never changes is worth more than a tidy join,
    because the outbound queue, the history table and the shadow copy all point
    at it, and none of them should need rewriting mid-flight.

  Where I will push back

  - If you pick B, I will argue the primary key rewrite is a real hazard: it
    happens exactly when the system is busiest, draining after an outage, and a
    partial rewrite leaves history rows orphaned.
  - If you want to rely on C without checking it, I will argue that it changes
    the outbound path's shape and belongs behind a verified claim, since an
    external ID field has to exist on the object and be configured in the
    client's org.

  What do you want the primary key to be, and should the design lean on a
  Salesforce external ID field if the client confirms one exists?

  The upsert facts came back verified

  - A PATCH to the upsert resource keyed on a custom external ID answers 201
    when it created a record.
  - A value matching more than one record answers 300 and writes nothing, which
    gives the duplicate case a defined outcome.
  - A field marked External ID and Unique works as a unique index and blocks
    duplicates. Without Unique, the caller needs View All Data permission, so
    "unique" belongs in the request to the client, not just "external ID".
  - Status code on an update differs by API version: 204 with no body on version
    45.0 and earlier, 200 with a body carrying a created flag from 46.0 on. The
    client's API version has to be pinned before anyone writes the response
    handling.

  Your webhook case, and where I push back

  - Your framing treats an unmapped recordId as an error case. It is the normal
    case.
    - Every record a sales user creates in Salesforce arrives with an ID we have
      never seen.
    - Park-and-retry would park every inbound create and wait for a mapping that
      will never appear.
  - Matching on Portal_Id__c carried in the webhook is the cheap answer, and I
    would not build on it.
    - The brief's sample payload carries recordId and changedFields, nothing
      else.
    - The webhook is the client's own mechanism, so no documentation says what
      it can carry.
    - That makes it an assumption with no fallback, on the path that handles
      every create.
  - What I would build instead: an unknown Salesforce ID triggers a retrieve of
    that record.
    - A populated external ID binds the Salesforce ID to the portal UUID we
      already hold.
    - An empty external ID means a record born in Salesforce, so we insert it.
    - The retrieve is needed anyway on a changed-fields payload for a record we
      have never seen, since the payload carries a few fields and we need the
      rest.
  - One case that does get parked: a populated external ID pointing at a portal
    record already bound to a different Salesforce ID.
    - That is a duplicate contact in Salesforce, created before the upsert
      existed or by a race.
    - No automatic rule can pick a winner there.
  - One ordering detail worth stating now: the binding must happen even when the
    event is then dropped as our own echo.
    - The first event after our create is usually that echo, identified as the
      integration user under the D5 loop rule.
    - Dropping the event before binding leaves the mapping empty and the next
      event repeats the retrieve.
  - Portal_Id__c in the payload stays worth asking for, as Q16, since it saves
    one retrieve call per new record. The design does not depend on the answer.

  Next question: what happens when Salesforce rejects a write permanently?

  - Retries cover a Salesforce that is unreachable. A validation rule firing, a
    required field left empty, a picklist value the org does not hold, or a
    field the integration user cannot write are different: the same call will
    fail the same way forever.
  - The brief does not say what should happen to that edit. The portal user has
    already seen their save succeed.

  What the choice is between

  - Retry a fixed number of times, then park the edit in a table with the
    Salesforce error, and carry on with the rest of the queue. The record stays
    wrong in Salesforce until a person acts.
  - Park it and mark the record in the portal as out of step with Salesforce, so
    the finance or customer-success user who made the edit can see their change
    did not reach the sales team.
  - Roll the portal edit back to the last value Salesforce accepted, so the two
    systems agree again.

  Where I stand

  - Park plus a visible marker on the record. Rolling back destroys a human's
    work over a machine's rule, and the person who typed the value is the one
    who can fix it.
  - A permanent rejection must leave the outbound queue, or one poisoned record
    stalls everything behind it. That matters most during the drain after the
    outage.
  - Distinguishing permanent from temporary comes down to the status code:
    400-class means permanent, 500-class and timeouts mean retry. The 403 for
    API limit exceeded is the trap, since it is 400-class and genuinely
    temporary.

  What do you want to happen to the edit, and should the portal user see that

  Section 7: which edit is current when both sides change the same field

  The brief asks for this by name: "Say what you use to decide which edit is
  current, on a webhook and on a portal save. Name the field."

  What we have to compare

  - Salesforce side: occurredAt, the time Salesforce gives the event. It is in
    the sample webhook.
  - Portal side: the Postgres server timestamp drawn under the row lock, with
    the sequence number breaking ties (A10, decision D10).
  - Those two come from machines nobody synchronised, and that is the whole
    problem.

  Option A: last write wins per field, comparing occurredAt against the portal
  timestamp

  - Each field carries the timestamp and the actor of its current value. A
    change arriving with an older timestamp is written to history and does not
    become current.
  - Clock skew is measured instead of assumed: every Salesforce HTTP response
    carries a Date header, so the worker keeps a running estimate of the offset
    between their clock and ours and applies it before comparing.
  - Fits the brief's own words: one current value we can justify, and the
    earlier values kept.

  Option B: Salesforce wins every conflict

  - Salesforce is the client's system of record and the sales team is bigger, so
    the tie-break is settled before it happens.
  - No clock trust at all, which makes it the only option that cannot be quietly
    wrong.
  - A finance correction to a shared field loses to a stale sales edit, and the
    finance user has no way to tell it apart from a bug.

  Option C: each field has an owning side

  - City and status belong to finance, phone and email to sales, and the owner's
    value wins whatever the clock says.
  - The brief's scenario is exactly this: the finance person sets the city, the
    sales person changes the phone, both survive.
  - It needs the client to assign nine fields, and it surprises people when it
    fires, since an edit made in the wrong system quietly fails to stick.

  Option D: no automatic winner, the record is marked and a person picks

  - Nothing is ever lost or silently overwritten.
  - It misses the 30-second target for that field by definition, and at 30 edits
    a second on the Salesforce side, someone would spend their day on it.

  My pick, and the case against it

  - I would take A, last write wins per field by timestamp, with the loser
    written to history and the skew offset measured from the Date header. Ties
    go to Salesforce, so the outcome is deterministic.
  - Now the argument against it, which is stronger than I would like:
    - It makes correctness depend on a clock we do not own. If Salesforce's
      clock runs three seconds ahead and our offset estimate is wrong, every
      close conflict goes to Salesforce and nothing in the system would ever
      tell us.
    - occurredAt is documented nowhere, because the webhook is the client's own
      mechanism. The brief says it is "the time Salesforce gives the event",
      which may be the time the field changed or the time the event was sent.
      Those differ on a retry, and the brief says webhooks arrive out of order
      and repeat.
    - Resolution bites at this volume. If-Unmodified-Since compares to one
      second, and if occurredAt is one second too, 30 Salesforce edits a second
      produce ties constantly, so the tie-break stops being an edge case and
      becomes the rule.
    - The outage makes it concrete. A portal edit made five hours into the
      outage carries a five-hour-old timestamp. A Salesforce edit from an hour
      ago beats it, correctly by the rule, and the finance user sees their
      correction disappear with no explanation. B has the same outcome and at
      least never pretends a clock decided it.
  - Which is why C keeps pulling at me: it is the only option where the brief's
    own scenario cannot go wrong, and the only one that does not depend on a
    timestamp we cannot verify.

  What decides it for me is whether occurredAt is trustworthy, and that is a
  question for the client, not something I can settle here. If you want A, I
  will build it with the measured offset and a counter on how often conflicts
  resolve within one second, so the assumption is visible when it starts
  failing.

  modes are a work item the document does not have, and the conflict rule needs
  translation before comparison, not just a value copy. A wrong guess also means
  outbound writes fail with a 4xx and park, hitting the parked-count alarm.

  **5. How much of the existing portal do I change, and does its data migrate?**
  The design has the portal reading and writing this Postgres directly (section
  2), taking a per-record row lock, drawing a sequence under it, carrying
  per-field versions in its forms, refusing stale saves with a who-changed-what
  message, and showing an out-of-step badge. That is real work inside someone
  else's application. Questions: is the portal's codebase mine to change, is it
  the same database or a separate one, and does it already store customers and
  contacts record-level (so these rows need a migration into
  `record`/`field_value`/`field_history` with a cutover) or is this greenfield?
  *Why it changes the plan:* portal changes plus a live data migration could be
  larger than the sync worker itself, and section 3's build order says nothing
  about either. If the portal is a separate service on a separate database,
  A14's "talking only through Postgres tables" does not hold and the whole
  boundary is redrawn.

  **6. When an inbound change loses the conflict, does anything push our winner
  back to Salesforce?**
  Section 5 step 5 updates the shadow "either way, since the shadow is what
  Salesforce holds and not what we chose" — so after a losing inbound change we
  knowingly hold a different value than Salesforce, with no outbox row. Section
  10 states the opposite-direction rule firmly ("changes applied by catch-up
  never enter the outbound queue"), and section 7 only covers two portal users.
  So: does a Salesforce change that loses on timestamp trigger a corrective
  outbound write, or do the sides stay divergent until the next edit touches
  that field?
  *Why it changes the plan:* without a corrective write, the system does not
  converge, and the "out of step" flag in `record` would need to cover this case
  too. With one, there is a re-entrancy risk — the corrective write echoes back
  — that the loop rule has to be checked against. It is a few hours of code
  either way, but it is a behaviour I must not guess at.

  **7. Can the client actually make the four org changes, and by when? (Q4,
  Q15)**
  The document flags field history tracking (C10/Q4) and the external ID field
  (C25/Q15) as assumptions, and A4 calls tracking "the assumption that matters
  most in the whole document". For planning I need the answer, not the flag:
  tracking on for all nine fields today, retroactively? An External ID + Unique
  custom field approved on Contact and Account? And how long client-side config
  changes take to land.
  *Why it changes the plan:* each has a stated fallback that is a materially
  different build — no external ID means claim rows plus a reconciliation query
  instead of upsert; no tracking means synthetic history entries and dropping
  the 243-call history path entirely. I cannot sequence section 3 without
  knowing which branch I am on, and these are long-lead client approvals.

  **8. What do I get to develop against?**
  No sandbox, credentials, API version, or auth flow is named. C24 makes the API
  version load-bearing on response parsing (204 empty vs 200 with a `created`
  flag). Also needed: the API names and types of the nine fields, whether
  "customer" really is Account (C11 is an assumption), and whether Person
  Accounts are enabled — they would change the Contact model.
  *Why it changes the plan:* no sandbox means everything is built against the
  fake Salesforce and the real-org risk lands late, which changes how I stage
  and estimate verification. Person Accounts in particular would break the
  contact-belongs-to-customer field.

  **9. Is the initial load of 5 million records in scope? (Q10)**
  The document leaves this open and I cannot close it myself. If it is in, it is
  a workstream with its own throttle, its own matching rules for records that
  already exist on both sides with no shared key, and a watermark handoff.
  *Why it changes the plan:* it roughly doubles the project and it competes for
  the same 100 calls a second, so it also changes the operating point in A1.

  **10. What should happen when a record is deleted in Salesforce?**
  Deletes are out of scope (section 12), but the outbound path is an upsert
  keyed on external ID. Any later portal edit to a record deleted in Salesforce
  silently recreates it. Is that acceptable for now, or does out-of-scope mean
  the record should park?
  *Why it changes the plan:* small code either way, but it is a data-correctness
  behaviour that would be found in production rather than review, and the
  catch-up poll will not see deletes at all.
